# DDOT FY2026 Construction Permit Approval Performance — Tableau Assessment

## 1. Purpose and requested deliverable

This project addresses the DDOT CS-12 Data Scientist Tableau assessment for the Associate Director of the Public Space Division. It measures average **business days to approve** new construction permits issued in fiscal year 2026, compares construction activity categories, and explores monthly application cohorts. The required deliverable is a **packaged Tableau workbook (`.twbx`) with at least three worksheets and one dashboard**, delivered in `FirstName_MiddleInitial_LastName_Tableau.zip`.

**Reporting window:** applications on or after 2025-10-01; issued dates 2025-10-01 through 2026-09-30 (FY2026). The extraction is a snapshot dated **2026-10-14 UTC**. The numbers and chart interpretations in this documentation are preliminary pending the validation limitations described below.

## 2. How to open and use the result

1. Unzip the submission to a local folder.
2. Open `DDOT_FY2026_Construction_Permit_Analysis.twbx` using Tableau Desktop or another compatible Tableau application. The candidate must supply this workbook from Tableau; it is **not** generated by the documentation package.
3. Open the dashboard named `DDOT FY2026 Approval Dashboard` (or the actual dashboard name inside the workbook).
4. Review the overall average approval KPI and distinct-permit KPI; compare average business days by construction activity; review the monthly application-cohort chart and tooltips.
5. If an Activity Category filter is included, test it and note which views respond. Filter behavior must be verified in the submitted workbook.
6. Read the methodology and limitations before treating the apparent monthly decline as a process improvement.

## 3. Source and inclusion criteria

**Data source:** DDOT TOPS, Public Space Construction Permits, ArcGIS REST Layer 23: https://maps2.dcgis.dc.gov/dcgis/rest/services/DCGIS_APPS/DDOT_TOPS/MapServer/23

Python requests use the layer's `/query` endpoint. Inclusion query:

```sql
ApplicationDate >= TIMESTAMP '2025-10-01 00:00:00'
AND IssueDate >= TIMESTAMP '2025-10-01 00:00:00'
AND IssueDate < TIMESTAMP '2026-10-01 00:00:00'
AND PermitType = 0
```

`PermitType=0` is the source code for New. Historical issuance is inferred from IssueDate rather than limiting results to the _current_ `Issued` status: the extract includes expired, suspended and revoked records that were previously issued. Whether reissues or renewals require further exclusion remains to be confirmed with DDOT definitions.

## 4. Why Python was used

The public ArcGIS REST feed has query-size/pagination limits and returns repeated location-level rows. Python provided a reproducible way to (a) download the complete matched record set in small batches, (b) audit and deduplicate permit records, (c) exclude weekends and DC holidays, (d) derive interpretable activity categories, and (e) generate verification tables and a single permit-level CSV for Tableau. **Tableau was used for presentation and interactive descriptive comparisons, not as the primary data-cleaning engine.**

## 5. Reproduction workflow

The scripts use Python 3 and the packages `pandas`, `numpy`, and `requests`:

```powershell
py -m pip install pandas numpy requests
```

**Step 1 — `step1_extract_audit.py`**: Requests matching OBJECTIDs; fetches records in batches of 150 using HTTP GET; saves raw candidate CSV and `audit_summary.json`. A prior attempt with 2,000 IDs in one URL failed with **HTTP 414 Request-URI Too Long**; reducing batches to 150 resolved the request-size issue. The original server-side count was 28,277 rows.

**Step 1 review (generated exploratory output):** 28,277 location-level rows; 5,378 distinct tracking numbers; 22,808 exact repeats when ignoring OBJECTID; 36 permits related to multiple wards. The project retained a permit-level table and separate ward relationship table to avoid counting repeated location records as repeated approvals. This review/deduplication was performed as an exploratory processing step; no standalone deduplication script is provided in this package, so the supplied permit-level preliminary CSV is a reproducibility input for Step 2.

**Step 2 — `step2_business_days.py`**: Reads `fy26_permit_level_preliminary.csv`; converts application/approval dates; calculates `ApprovalBusinessDays` from `ApplicationDate` to `LastApprovalDate`, excluding Saturdays, Sundays and the DC public holidays coded in the script. Counting convention: exclude application date, include approval date if eligible; same-day approval = 0. Flags invalid dates and durations above 90 business days; saves preliminary CSV and audit JSON. Holiday list and sources are in the script. Confirm the list against any applicable agency-specific closures.

**Step 3 — exception review:** `step3_validation_findings.json` compares calculated business days and the source's `DaysToApprove` to simple calendar differences. Of 5,378 permits, 4,939 source values matched calendar-day differences; 439 did not. The source matched calculated business days for 3,320, disagreeing for 2,058. A 37-row exception sample was produced for potential external permit-history review. **The sample was prepared, but individual online permit histories have not been documented as verified.**

**Step 4 — `step4_classify_permits.py`**: Reads Step 2 CSV, splits the `TypeDetailNames` activity descriptions and uses the prefix before `;` as the activity family. If exactly one family is present, assigns that family. Mixed families are labeled `Multiple activity categories`. Creates `ApplicationMonthStart`, `tableau_permit_analysis_preliminary.csv`, `category_summary.csv`, `month_summary.csv`, and `activity_category_audit.json`.

**Step 5–8 — Tableau:** Connect Tableau to `tableau_permit_analysis_preliminary.csv` as a Text File. Validate types: `TrackingNumber` text, `ApprovalBusinessDays` numeric, `ActivityCategory` text, `ApplicationMonthStart` date. Build (1) a text KPI with `AVG(ApprovalBusinessDays)` and, optionally, a distinct permit-count KPI using `COUNTD(TrackingNumber)`; (2) horizontal bars with `ActivityCategory` on Rows and `AVG(ApprovalBusinessDays)` on Columns, sorted descending; (3) a continuous month timeline with `MONTH(ApplicationMonthStart)` and `AVG(ApprovalBusinessDays)`; (4) a tiled dashboard with KPIs, charts, captions, findings, and a methodology statement. Tooltips should contain permit counts. Package as `.twbx` and reopen it to verify embedded data.

## 6. Preliminary QA and descriptive findings

- Raw query records: **28,277**; distinct permit tracking numbers: **5,378**; missing application, approval or issue dates in the extracted records: **0**.
- Unique-record current statuses: **2,967 Issued; 2,408 Permit Expired; 2 Suspended; 1 Revoked**.
- Mean computed approval duration: **11.40 business days**; median: **1**; 90th percentile: **40**; >90-business-day permits: **107**.
- Activity groups: **Excavation 4,538 (10.89 days)**; Multiple activity categories 399 (13.70); Over Head Work 202 (8.39); Paving 97 (18.77); Fixture 94 (22.55); Projections 26 (12.69); Landscaping 20 (23.90); Mega Projects 1 (0.00); PS Rental 1 (0.00).
- The bar chart excludes **Mega Projects and PS Rental** because each category contains one permit. They remain in the overall population.
- Monthly cohort averages peak in December 2025 (82.48 business days, **n=33**) and are much lower for September 2026 (0.91, **n=1,000**). These comparisons may be strongly affected by only including permits issued by FY2026 end: later-submitted permits had a shorter window in which long-duration approvals could enter the issued population. **Do not interpret the decline as proven operational improvement.**

## 7. Known limitations and unfinished validation

1. `LastApprovalDate` is a **provisional** approval endpoint; definitions and same-day counting conventions should be verified against authoritative TOPS permit histories.
2. Source `DaysToApprove` is frequently closer to calendar days than independently computed business days; differences may also involve timestamps or source business rules. This does **not** establish an error in the source.
3. One `TrackingNumber` is treated as one application; confirm whether that is the intended DDOT reporting entity and how amendments/reissues are represented.
4. `PermitType=0` plus FY26 issue date is an operational interpretation of new permits issued in FY26; verify eligibility rules with the agency.
5. Observed holiday schedule excludes listed weekdays; agency closures beyond public holidays are not modeled.
6. Current statuses were not used to exclude previously issued permits; the REST feed may change between extractions.
7. The screenshot-based dashboard development is not equivalent to a full audit of the final `.twbx`; verify dashboard filters, embedded extract, and final display within Tableau.
8. Ward-level comparisons require separate careful treatment because some permits have multiple ward relationships.
